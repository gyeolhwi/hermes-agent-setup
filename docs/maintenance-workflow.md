# 유지보수 업무 워크플로우

이 문서는 Hermes를 웹사이트·서비스 유지보수에 활용할 때의 **안전한 공통 흐름**입니다. 특정 회사, 고객사, 서버, 메일함, SFTP 서비스에 종속되지 않습니다.

기본 원칙은 간단합니다.

```text
접수 → 기록 → 조사·백업 → 명시적 승인 → 변경 → 실제 검증 → 검수 → 완료
```

## 역할 분리

| 기록 | 역할 |
|---|---|
| GitHub Issue | 요청 내용, 승인, 변경 사항, 검수 결과의 기준 기록 |
| Slack 스레드 | 작업 중 대화와 짧은 진행 알림 |
| Hermes | 조사·초안·파일 확인·검증 보조·증적 정리 |
| 사람 | 변경 승인, 계정 로그인, 최종 검수·외부 발송 판단 |

GitHub Issue와 Slack을 연결하려면 [Issue ↔ Slack 웹훅 안내](github-issue-slack-webhook.md)를 사용합니다.

## 1. 요청 접수와 기록

요청을 받으면 먼저 Issue 하나에 아래를 정리합니다.

```text
대상 서비스 또는 URL
요청한 변경 내용
변경할 파일·화면 위치
제공된 자료와 적용 일정
완료 판단 기준
확인할 모호한 점
```

요청을 Issue로 기록하는 일은 **작업 시작 승인과 다릅니다.** 아직 서버·웹사이트·메일에 영향을 주는 작업을 실행하지 않습니다.

## 2. 조사와 변경 전 백업

Hermes는 실제 변경 전에 대상과 현재 상태를 확인합니다.

- 실제 페이지·기능·파일 위치를 확인
- 요청 자료와 적용 위치가 맞는지 확인
- 수정 대상 파일만 별도로 백업
- 백업본과 업로드·수정할 파일을 분리
- 모호한 자료나 대상은 추측하지 않고 Issue에 질문으로 남김

전체 서버 복구본과 변경 전 파일 백업은 목적이 다릅니다. 전체 복구본이 있더라도, 이번 변경에 직접 관련된 파일은 별도로 보관합니다.

## 3. 명시적 승인

다음 행동에는 요청자의 명시적 승인이 필요합니다.

```text
운영 서버 파일 수정 또는 업로드
외부에 보이는 콘텐츠 공개
고객·외부 사용자에게 메일 발송
원격 백업 파일 삭제
```

`Issue 생성`, `조사 완료`, `백업 완료` 같은 상태는 승인으로 해석하지 않습니다. 승인 내용은 Issue 또는 연결된 Slack 스레드에 남깁니다.

## 4. 변경과 증적

승인 뒤에만 변경을 실행합니다.

1. 승인된 파일·설정만 수정하거나 업로드합니다.
2. 실제 적용한 파일과 변경 전 백업을 혼합하지 않습니다.
3. 무엇을 바꿨는지 Issue에 짧게 기록합니다.
4. 텍스트 변경이라면 변경 전·후 문구를 함께 남깁니다.

## 5. 실제 검증

파일 존재, HTML 문자열, 배포 성공 메시지만으로 완료를 판단하지 않습니다.

```text
브라우저에서 실제 화면 확인
버튼·링크·폼 등 요청된 상호작용 시험
이미지·배너·반응형 화면 확인
변경 대상 URL과 시간 기록
```

작업 결과가 의도와 다르거나 검증이 불가능하면 성공으로 보고하지 않고 `검수대기` 또는 `수정 필요` 상태로 남깁니다.

## 6. 검수와 완료

권장 상태 흐름입니다.

```text
작업준비 → 작업중 → 검수대기 → 완료
                 └→ 수정요청 → 작업중
```

- **작업준비:** 요청 기록, 조사 또는 백업까지 완료
- **작업중:** 명시적 승인 뒤 변경 실행 중
- **검수대기:** 적용과 운영자 검증은 끝났고 요청자 확인 대기
- **수정요청:** 검수 결과 추가 변경 필요
- **완료:** 요청자 승인과 필요한 증적이 모두 확인됨

Issue↔Slack 연결을 쓴다면 완료 시 같은 Slack 부모글에 `✅`를 추가하고 스레드에 완료 요약을 남깁니다. Slack 완료 처리나 증적 기록이 실패했다면 Issue를 완료로 닫지 않습니다.

## 자동화의 경계

자동화하기 좋은 일:

```text
Issue·Slack 연결
변경 전 백업 목록 작성
페이지·링크·파일 검사
증적 초안과 작업 요약
상태 변경 알림
```

사람이 결정해야 하는 일:

```text
모호한 이미지·파일의 실제 적용 위치
운영 반영 승인
고객·외부 메일 발송
검수 승인
원격 백업 삭제
```

이 원칙을 지키면 Hermes는 반복 업무를 줄이면서도, 운영 변경의 결정권은 사람에게 남깁니다.
